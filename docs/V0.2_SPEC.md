# rekey v0.2 — Architecture Spec
*Consolidated from three parallel research tracks (May 2026). Decisive design for the harness-led rewrite.*

---

## 0. Why we're rewriting (briefly)

v0.1 is agent-led: the LLM gets one big task prompt and decides everything. Live testing on Snapchat surfaced four real failure modes that an agent-led design cannot fix:

1. **Vault had a stale current password.** Agent recovered (switched to forgot-password) but only because we hard-coded that branch in the prompt — every new branch is a prompt update.
2. **OTP fetcher used `from:accounts.snapchat.com`** which matched no email (Snapchat sends from a different domain). Agent fell back to `pause_for_human`. Architecture wasn't the bug; the OTP layer was naive.
3. **Snapchat returned a generic "Something went wrong"** on submit. Agent retried once (per prompt instruction) and stopped — but the right move on a high-stakes endpoint is *zero* retries + diagnosis. The retry was a coin-flip into a possible lockout.
4. **Dashboard handoff future timed out at 180s** (browser-use step timeout) while the actual page advanced. Mismatch between the LLM step model and the long-lived human-approval model.

Across the broader landscape: the variability of real password-reset flows (10 flow categories, ~25 distinct edge cases, password rules that bite, anti-bot endpoints that lock accounts) means a fixed task prompt is the wrong abstraction. **Code must own the state machine. The LLM is called surgically for hard, local decisions only.**

The published 2026 benchmark for hybrid (Playwright + Claude) is **92% reliability** vs. browser-use at 89% — meaningful, but the much bigger gain is in *debuggability, cost, and lockout safety*, not raw success rate.

## 2. The state machine (concrete)

Replace the single `Agent.run(task_prompt)` call with an explicit state machine.

```
PENDING
  ↓
DISCOVER_SITE                  # classify: known recipe? new site? OAuth-only?
  ↓
PICK_STRATEGY                  # in-session | forgot-password | manual-handoff
  ↓
 ┌─[in-session]──────────────────────────────────────┐
 │ AUTHENTICATE                                       │
 │   verify: logged-in indicator visible              │
 │ NAVIGATE_TO_CHANGE_PW                              │
 │   verify: form with ≥2 password inputs visible     │
 │ READ_POLICY                                        │
 │ GENERATE_PASSWORD (iterative; see §6)              │
 │ FILL_FORM                                          │
 │   verify: fields populated, no client-side error   │
 │ SUBMIT      ← high-stakes; 0 retries (see §5)       │
 │   verify: 2xx on POST + success URL/DOM            │
 │ VERIFY_INDEPENDENTLY     ← gold standard           │
 │   verify: clean-context login with new pw succeeds │
 │ PERSIST_TO_VAULT                                   │
 │ DONE                                               │
 └────────────────────────────────────────────────────┘
 ┌─[forgot-password]────────────────────────────────────┐
 │ NAVIGATE_TO_FORGOT                                   │
 │ ENTER_EMAIL                                          │
 │ AWAIT_OTP_OR_LINK   ← Channel Layer (§4)             │
 │ NEW_PASSWORD_FORM   ← as above from READ_POLICY      │
 │ … → DONE                                             │
 └──────────────────────────────────────────────────────┘
 ┌─[manual-handoff]─────────────────────────────────────┐
 │ Open the change-password page in user's browser,     │
 │ pre-fill what we can, surface a "take over" prompt   │
 │ in the dashboard, wait for completion.               │
 └──────────────────────────────────────────────────────┘
```

**Failure branches** (any state → these):
- `DIAGNOSE_FAILURE` — one frontier-model call with DOM + screenshot + last network response → returns `{cause, recoverable, next_action}`.
- `SWITCH_STRATEGY` — e.g., in-session → forgot-password. Each strategy can fire once per attempt.
- `ESCALATE_TO_HUMAN` — surface to dashboard with full trace bundle.
- `LOCKOUT_DETECTED` — abort, never retry, mark the site cooldown (24h).

Implementation: **hand-rolled Python state machine** (~300 LOC). Don't take on Burr / LangGraph / Temporal at this scale; revisit if the graph grows past ~25 states or we need durable multi-day resumption (Temporal). Use plain dataclasses + enum + dispatch dict.

## 3. Per-state verification — the single biggest design change

**Verification is a fact, not an LLM judgment.** Every state transition has an explicit postcondition checked deterministically.

Verification primitives, cheapest-first:

1. **URL change** — strongest cheap signal. `page.url.startswith("/account/success")`.
2. **DOM presence/absence with auto-wait** — Playwright-style `expect(page.getByText("Password updated")).toBeVisible({ timeout: 5000 })`.
3. **Network response via CDP** — observe the actual `POST /change-password` and assert 2xx + parse the response body. The site UI lies; the network does not.
4. **Visual / vision check** — small LLM call against a screenshot, last resort for ambiguous states.
5. **Fresh-context login test** — final terminal verification: open a clean Playwright context (no cookies), attempt login with the new password. If that fails, the change didn't happen — don't write to the vault.

Implementation rule: **never write to the vault before step 5 passes.** v0.1's `_is_successful(history)` check (just calls `history.is_successful()`) is the exact wrong pattern — the LLM said it worked, we believed it. v0.2 demands an independent observation.

Borrow the Playwright `expect.toPass({ retries: N })` pattern for assertions: poll the postcondition with timeout, never the action.

## 4. OTP / verification channel layer

Replace the single `WebmailTabOTPFetcher` with a `VerificationChannel` abstraction that can resolve from any of: email (multiple providers), iMessage/SMS, TOTP, push, KBA store, manual entry. The flow engine pauses with `await needs(channel='email_otp', sender_hint='snap.com', within=120s)`; any registered channel can resolve.

### Primary paths (in priority order)

| # | Channel | How | Why | Latency |
|---|---|---|---|---|
| 1 | **TOTP from vault** | `op item get <id> --otp` / `bw get totp <id>` / `pyotp` on local secret | Strictly best when available — zero network, deterministic | <100ms |
| 2 | **iMessage / SMS via `chat.db`** | Read-only SQLite at `~/Library/Messages/chat.db` + FSEvents watch | macOS Continuity forwards SMS to Mac — direct read works; the user has this configured | <1s after delivery |
| 3 | **Apple Mail.app Rule + AppleScript handler** | Install a Mail rule that POSTs each incoming message to `http://127.0.0.1:<port>/mail-event` | Provider-agnostic (iCloud, Gmail, Outlook, Fastmail — anything Mail.app handles), push-based, no OAuth | <2s after delivery |
| 4 | **Gmail XOAUTH2 + IMAP IDLE** | Standard OAuth desktop-app flow → persistent IDLE connection | Personal-use exemption for CASA (Google explicitly: <100 known users → no verification). Push-equivalent latency without the API quota. | 1–3s |
| 5 | **Webmail-tab DOM scrape** (current v0.1) | What we have today | Last resort only; brittle, 2/5 reliability | 2–5s |

Manual entry (dashboard) is always available as the final fallback.

### Critical bug fixes from v0.1 → v0.2

- **The `sender_hint` was the site host**, not the email domain. Fix: drop the sender filter by default and instead score recent inbox emails by (a) recency (last 60–120s), (b) cue-word proximity (`verification|otp|code|passcode|security|sign-in`), (c) domain relatedness — generated heuristically, not from a passed string.
- **`document.body.innerText` reads only the inbox-list view** (snippets are truncated, the code is often past the boundary). Fix: open the most recent email itself OR use a real API/database path that returns the full body.
- **The OTP regex `\b(\d{4,8})\b`** has false positives (tracking numbers, years, phone fragments). Use the cue-word-proximity rank from the research:
  ```
  (?<![\d-])\b(\d{4,8})\b(?![\d-])
  ```
  with a +1/+3/+5 score boost for proximity to verification-cue words, plus rejection of values that match year/phone patterns.

### Permissions setup we'll require from the user

- Full Disk Access on Terminal/iTerm (for `chat.db` SQLite read on Sequoia+)
- Automation permission for Mail.app (one prompt on first AppleScript invocation)
- Gmail OAuth (one browser consent, token stored in macOS Keychain)

Document all three in SETUP.md with screenshots.

## 5. Retry & lockout policy — *the safety-critical design*

This is where v0.1 was naive. Real lockout policies: banking sites 3 attempts → permanent lock; X 5 → 24h; Microsoft 5 → 24h; Snapchat → silent rate-limit with `Something went wrong`. The standard RPA default of "3 retries with backoff" is *catastrophic* on a 3-strike lockout.

### Per-step retry budgets

| Step kind | Retries | Backoff | Notes |
|---|---|---|---|
| Idempotent navigation (click, scroll, switch tab) | 3 | 1s/2s/4s + jitter | Tenacity-style |
| Form fill (text input) | 2 | 0.5s | Clear field between attempts |
| **Submit on a high-stakes endpoint** | **0** | — | Diagnose first; never blind-retry |
| Verification poll (assertion) | N/A | 0.5s | Up to per-state timeout |
| OTP wait (channel) | N/A | 0.5s poll | Up to `window_seconds` |

### What happens on submit failure

Don't retry. Run `DIAGNOSE_FAILURE` once (one frontier-model call with DOM + screenshot + last network response + observed error text). The diagnosis returns a typed result:

```python
@dataclass
class FailureDiagnosis:
    cause: Literal["password_rule_violated", "rate_limited", "captcha_required",
                   "step_up_2fa", "session_expired", "unknown"]
    recoverable: bool
    next_action: Literal["regenerate_password", "switch_strategy",
                          "wait_and_retry_once", "escalate_to_human", "abort"]
    evidence: str
```

State machine acts on `next_action`. **Only `regenerate_password` and `switch_strategy` ever take another shot at the same endpoint.** `wait_and_retry_once` waits a sensible duration (typically 5+ minutes) and only fires for transient causes, capped at 1 total retry per attempt.

### Per-site circuit breaker

Use **PyBreaker**: after 2 hard failures on the same domain within 24h, freeze it (mark `cooldown_until`). User can manually override.

### "Bot-intensity tier" → default to handoff

Static per-site classification (from the taxonomy research):

| Tier | Sites | Default strategy |
|---|---|---|
| **Severe** | Banks, brokerages, Coinbase/Binance, Snapchat, X, Instagram, TikTok, Google/Microsoft/Apple primary accounts | **Manual handoff** — don't even attempt automated flow. We pre-fill what we can and surface a "take it from here" prompt. |
| **Moderate** | LinkedIn, Amazon, eBay, healthcare portals | Attempt with conservative retry; escalate on any anomaly. |
| **Light** | Most B2B SaaS, streaming services, forums, dev tools | Full automated flow. |

This ships as a YAML/JSON config in the repo. Users can override per-credential.

## 6. Password generation — *iterative, policy-aware*

v0.1 generates blindly, submits, fails on sites with weird rules. v0.2:

1. **Per-site policy database** — seeded from [dumbpasswordrules.com](https://dumbpasswordrules.com/sites-list/) (Chase: no consecutive same-class chars; BofA: 20 max truncates silently; Cigna: 12 max; Itaú: exactly 8 digits; …). YAML config in the repo, easy to extend.
2. **Live parse** — at `READ_POLICY` state, extract from the form: `pattern`, `minlength`, `maxlength`, visible bullet lists of requirements, adjacent help text. LLM extract with Pydantic schema (small model — Haiku or Gemini Flash). Merge with the static database.
3. **Generate iteratively** — try the strongest password the merged policy allows. On rejection, parse the error text (or the changed DOM node), update policy, re-roll. **Cap at 3 generation attempts** to avoid lockout.
4. **Never exceed observed `maxlength`** — even if the form silently accepts more, sites that truncate (BofA, Best Buy, MKB) will leave you locked out.
5. **Cross-check banned chars** — generated pw must not contain any character the policy forbids.

Implementation: pure Python module, no LLM in the generation loop itself (only in policy parsing).

## 7. LLM sub-agent decomposition + model tiering

The cost / reliability sweet spot is **model tiering**: frontier for rare, hard decisions; cheap for many, simple ones; *no model at all* for deterministic steps.

| Decision | Model tier | When |
|---|---|---|
| Plan a flow for a brand-new unknown site | **Frontier** (Opus / GPT-5.5) | Once, cached as a recipe |
| Diagnose `Something went wrong` | **Frontier** | One-shot, never in a loop |
| Locate the change-password form on settings page | **Mid** (Sonnet 4.6 / Gemini 2.5 Flash) | Per attempt, cached selectors |
| Extract password policy from tooltip / help text | **Mid** | Per attempt |
| Classify "is this a CAPTCHA page?" | **Small** (Haiku 4.5 / Gemini Flash) | Per page load |
| Read an OTP from email body | **None** (regex + scoring) | Always |
| Decide whether to enter forgot-password fallback | **None** (state-machine rule) | Always |

For the surgical use case, prefer **Stagehand-Python**'s `act()`/`extract()`/`observe()` primitives — they're built exactly for this pattern (deterministic when possible, AI when needed, with structured-output schemas). browser-use's `Agent` becomes the fallback `agent()` mode in Stagehand.

**Library decision**: migrate from `browser-use` to **`stagehand-python`** for the browser layer. browser-use is fine for the agent-led pattern; Stagehand's primitives map better to a harness-led pattern. (Both wrap Playwright + CDP — moving is a few hundred LOC, not a rewrite.)

## 8. Observability

Multi-step flows fail in subtle ways. v0.1 has only stdout logs. v0.2:

| Layer | Tool | Always-on? |
|---|---|---|
| Per-state events | JSON-Lines file: `{ts, state, action, params, result, postcondition_result, llm_calls[], duration_ms}` | Always |
| Browser trace | Playwright Trace Viewer trace per run (one HTML, scrubbable, includes screenshots + DOM + network + console) | Always |
| LLM tracing | **Langfuse** self-hosted (MIT, free up to 50k events/month) | Always |
| Screenshots | On state entry + on every postcondition failure | Always |
| HAR file | CDP-captured for the SUBMIT state only | On-demand (config) |
| DOM snapshot | On postcondition failure | Always (cheap) |

Replay capability: re-run the state machine against recorded (state, page snapshot, LLM IO) tuples — Playwright Trace Viewer covers the browser side; Langfuse covers the LLM side; the JSON-Lines event log threads them together.

## 9. Sub-spec: "site recipe" format

Per-site recipes accelerate known flows and let us hand-tune the long tail of edge cases without changing the core code. Recipe shape (YAML):

```yaml
site: snapchat.com
display_name: Snapchat
bot_intensity: severe       # → default to manual-handoff (§5)
strategies: [forgot-password]   # in-session blocked by design
forgot_password_url: https://accounts.snapchat.com/v2/forgot-password
selectors:
  email_field: [name=email, '[autocomplete=email]', 'input[type=email]']
  submit: ['button[type=submit]', 'text=Continue']
  otp_field: ['input[autocomplete=one-time-code]', 'input[name=verification_code]']
  new_password: ['input[name=new_password]', 'input[type=password]:nth-of-type(1)']
  confirm_password: ['input[name=confirm_password]', 'input[type=password]:nth-of-type(2)']
password_policy:
  min_length: 8
  max_length: 128
  forbidden_chars: ""
otp:
  expected_sender_domains: [snapchat.com, snap.com]
  cue_words: [snapchat]
  ttl_seconds: 300
verification:
  success_url_contains: /success
  success_text: ["Your password has been changed"]
```

Bootstrap: ship recipes for ~30 high-frequency sites in v0.2; auto-learn unknown sites (frontier-model plan, cached as a recipe, user reviews and commits).

## 10. Library decisions (summary)

| Concern | v0.1 | v0.2 |
|---|---|---|
| Browser automation | browser-use 0.12 | **Stagehand-Python** on Playwright (migrate) |
| LLM provider | OpenAI gpt-5.5 default | **Tiered**: Sonnet 4.6 for mid, Haiku for small, Opus/GPT-5.5 only for frontier roles |
| State machine | Implicit in LLM task prompt | **Hand-rolled Python** (no Burr/LangGraph yet) |
| Retries | One cautious retry in prompt | **Tenacity** with per-step policy |
| Circuit breaker | None | **PyBreaker** per-domain |
| OTP — email | DOM-scrape Gmail tab (broken) | Tiered: TOTP → chat.db → Mail.app rule → Gmail XOAUTH2 → DOM scrape |
| OTP — SMS | None | **SQLite `chat.db`** + FSEvents |
| TOTP | None | `op`/`bw` CLI + `pyotp` |
| Observability | stdout logs | JSON-Lines + Playwright Trace Viewer + **Langfuse** |
| Verification | Trust the LLM | Code postconditions + fresh-context login test |
| Per-site config | None | YAML recipes (§9) |

Explicitly **not adopting**: Temporal (overkill), CrewAI/AutoGen (deprecated/coarse), LangGraph (too heavy for this scale), Anthropic computer-use (vision-based is less reliable than DOM-driven here).

## 11. Migration plan (phases)

**Phase A — Foundation** (target: ~1 week)
1. Migrate browser layer from `browser-use` to `stagehand-python`.
2. Implement the explicit state machine with two strategies (in-session, forgot-password) + diagnosis hook + circuit breaker.
3. Per-state verification (URL/DOM/network), fresh-context login as terminal.
4. Wire Tenacity + PyBreaker.

**Phase B — Channels** (~3–4 days)
5. `chat.db` SMS reader with FSEvents.
6. Apple Mail.app rule + AppleScript handler.
7. Gmail XOAUTH2 + IDLE (personal-use exemption).
8. TOTP via op/bw CLIs.
9. New `VerificationChannel` abstraction; the action layer routes to it.

**Phase C — Intelligence** (~4–5 days)
10. Iterative policy-aware password generation (live parse + static DB).
11. Bot-intensity classifier → default-to-handoff for severe tier.
12. Sub-agent model tiering with cost-aware routing.
13. Failure-diagnosis frontier call.

**Phase D — Observability + recipes** (~3–4 days)
14. JSON-Lines event log + Playwright Trace Viewer wiring.
15. Langfuse (self-hosted) for LLM tracing.
16. Ship 30 starter site recipes.

**Phase E — Hardening** (~1 week)
17. Iterative real-site testing: fitbit, manychat (if user adds), 5 light-tier sites, 3 moderate-tier sites. Skip severe-tier until manual-handoff UX is polished.
18. Replay/debug harness.
19. Docs (THREAT_MODEL.md update, SETUP.md update).

## 12. What v0.2 would have done differently on the Snapchat run

Walking through the same run with v0.2:

1. `DISCOVER_SITE` → loads `snapchat.com` recipe → `bot_intensity: severe`.
2. `PICK_STRATEGY` → recipe says strategies=[forgot-password] only AND bot_intensity=severe → **switches to `manual-handoff` mode** by default.
3. Dashboard surfaces: "Snapchat is on the high-anti-bot list. I've opened the forgot-password page and the OTP capture is armed (Mail.app rule + chat.db). Type your new password when you're ready and submit; I'll write it to your vault."
4. User completes the change in their own hands; rekey watches the network and confirms the change.
5. `VERIFY_INDEPENDENTLY` → fresh-context login → success.
6. `PERSIST_TO_VAULT`.

No 12-step gpt-5.5 agent loop. No `Something went wrong` retry. No coin-flip into lockout. The user spent 30 seconds with a guided UX; rekey did the boring parts (correct OTP capture, vault write, verification).

For a light-tier site (e.g., a small SaaS where there's no real anti-bot), the full automated flow runs end-to-end.

## 13. Open questions for you

These genuinely change the build; want your call before writing code:

1. **Stagehand vs. keep browser-use?** Stagehand has the better primitives for harness-led work, but adds a TypeScript-flavored dep (the Python port is newer). Trade-off: cleaner architecture vs. less moving parts.
2. **Gmail OAuth (personal-use exemption) vs. Apple Mail.app rule as primary?** Mail rule is provider-agnostic and simpler but requires one-time setup of an AppleScript file. Gmail OAuth is one-time consent in a browser. Both work; pick a default.
3. **Manual handoff for severe-tier sites — acceptable?** This is the biggest UX call. If you'd rather we *try* on banks/Snapchat/etc. and only handoff on failure, we keep them in scope but with hard retry-zero discipline. If "don't bother for those tiers" is OK, the spec gets much simpler.
4. **Langfuse self-hosted or cloud free tier?** Self-hosted is true local-first but adds a Docker dep. Cloud free tier (50k events/month) is plenty for personal use but means LLM call metadata leaves the laptop.
5. **Site recipes — ship ~30 starter sites in repo, or build the "first run on a new site stores a recipe" flow first?** Different sequencing of the same end state.

Tell me which of these to bias, and I'll start Phase A.
